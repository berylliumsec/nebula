# Nebula 3.0.0-alpha.11

Nebula 3.0.0-alpha.11 adds fail-closed OpenVPN egress for container-backed
terminals and automation, routes harness commands through Nebula's authoritative
runtime, and tightens the continuity of everyday operator workflows.

## Changes since alpha.10

- Operators can upload, name, inspect, select, and remove OpenVPN profiles from
  Settings. Profiles and optional username/password credentials are stored
  separately, secrets are not returned by the API, and deletion is blocked while
  a profile is actively selected or in use.
- Project network settings can select a VPN profile for container terminals and
  automation. Nebula starts OpenVPN inside the workload's network namespace,
  verifies the tunnel and split default routes before admitting commands, and
  denies non-tunnel egress if setup fails.
- OpenVPN profile validation accepts safe client directives used by common
  providers, including NordVPN ping timers and renegotiation settings, while
  rejecting scripts, plugins, externally referenced secrets, unsafe routing, and
  other host-affecting options.
- Terminal status makes the selected route, VPN identity, connection state, and
  recovery action visible. Human terminals and automation use the same certified
  egress boundary, including after reconnect and container-runtime startup.
- Harness commands now execute through Nebula's runtime interface instead of a
  parallel host-command path, preserving the selected Project workspace,
  permissions, container, network, and VPN policy.
- Linked Project folders remain the authoritative workspace for Files, Code,
  terminals, containers, harnesses, instruction discovery, and skills rather than
  being copied into a hidden parallel workspace.
- Conversations recover after command-runtime changes, keep Ask Nebula anchored
  to the active conversation, and support clearer interruption, continuation,
  mission-result handoff, and streaming Markdown behavior.
- The resource and action model now provides canonical identities, relations,
  shared actions, device-aware brokering, privacy-preserving handoffs, and a
  federated omnibox across operator-visible resources.
- Settings gained searchable navigation and the Zero Dark theme. Native browser
  surfaces remain correctly layered beneath the settings lens.
- Security Browser gained a managed-runtime foundation and a clearer Prepare /
  Retry readiness flow; this does not silently provision a missing browser or
  proxy runtime.

Existing Projects, conversations, Evidence, Findings, Reports, browser research
state, VPN profiles, and linked workspace data are preserved. This candidate adds
database migrations for canonical resource relations and search documents; the
release workflow exercises SQLite and PostgreSQL upgrade and downgrade paths.

## Native packages

The release workflow stages the following artifacts for manual review:

- a Linux x86_64 AppImage for direct distribution; and
- a Linux x86_64 DEB for managed distribution.

Direct builds can consume Nebula's signed updater channel. Managed builds omit
the direct updater so deployment remains under administrator control. macOS,
Windows, Linux arm64, RPM, Flatpak, Snap, Homebrew, and browser extensions are not
included in this alpha.

The packaged desktop includes the Chromium runtime required for rendered URL
sources. Docker or Podman is required for terminal, automation, VPN, and isolated
debugger features. OpenVPN support requires the Nebula container image shipped
for this release. A model provider or supported assistant harness remains
optional.

## Deliberate boundaries and alpha limitations

- This is a prerelease and may contain compatibility defects or incomplete UX.
- VPN routing applies to the selected container workloads, not to the Nebula host
  or the browser device used to operate Nebula remotely.
- Uploaded VPN profiles are treated as untrusted input. Unsupported or unsafe
  directives fail closed instead of being passed through to OpenVPN.
- VPN authentication requirements are provider-specific. Providers such as
  NordVPN may require separate service credentials rather than an account email
  and password.
- A successful VPN state certifies the workload network namespace and route;
  host-side commands remain outside that namespace by design.
- The protected release workflow does not build a macOS package. A macOS desktop
  build must be produced and verified through a separate supported distribution
  process before macOS availability is claimed.
- Physical iPhone Safari, physical macOS remote-Core, and provider-diverse VPN
  workflows remain manual verification gates; automated WebKit, macOS CI, and a
  live NordVPN check do not replace them.

## After installation

Launch the Linux desktop with `nebula`, then verify the bundled Core and local
execution boundary:

```console
nebula-core doctor --json
```

To verify a selected VPN from a Nebula container terminal, run:

```console
curl -4 https://api.ipify.org && echo
```

Compare that result with the same command on the Nebula host. Report defects with
the exact version, platform, failed action, correlation ID, and a Diagnostics
support bundle after reviewing it for sensitive engagement data.
