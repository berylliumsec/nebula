# Phase 4 — Core follow-up queue

Operator journey: queue a drafted message with selected context, edit/reorder on either device, explicitly resume, close both viewers, return to sequential durable replies. Core owns claims and dispatch; queue linkage is written in the same transaction as the turn. Duplicate keys cannot submit different content. Restart ambiguity, failures, revoked device grants, changed profiles, approvals and active turns prevent blind draining. Imported browser entries are paused; uncertain entries require review and explicit retry as a new message.

Validation: 43 Python tests passed across chat, API, workspace and queue; 10 component tests passed. Queue-specific tests cover stale/two-device writes, duplicate keys, rollback on concurrent pause, sequential provider execution with no browser, harness dispatch with selected context, restart before/after durable turn creation, failed/interrupted turns, pending approval, capability changes, revocation and conversation deletion. Production build, Ruff and frontend diagnostics audit pass. Integration hardening also formats the prior phase's new Python files, classifies frontend errors and preserves newer session metadata during asynchronous naming.
